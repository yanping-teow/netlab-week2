Assignment Reflections

1. Data Model vs. Serialisation

The data model of UM-Campus-Core-Net is three switches (s1 core, s2 and s3 access), six hosts with IPv4, IPv6 and MAC addresses, and the links between them. topology.yaml and topology.json are two serialisations of that same model: building from either file gave the same network and the same pingall result (0% dropped, 30/30). Only the syntax differs. The one thing the JSON lost is the comment in the YAML explaining that s1 is the core and that I left out an s2-s3 link to make a tree. JSON has no comment syntax, but the network did not change, because comments were never part of the model.

2. Static Validation vs. Runtime Checks (IPv4 vs. IPv6 DAD)

check() reads the data before Mininet starts, so my bad.yaml (h6 copying h5's addresses, plus a link to a switch s9 that does not exist) is stopped with a PROBLEM message for each mistake and never gets built. Without that, the network would be built first, and I would have to notice a fault afterwards. At runtime I gave h2 h1's addresses. IPv6 noticed: fd00:3218::11 is marked dadfailed on h2 because Duplicate Address Detection asked the network first and found that h1 already had it. IPv4 has no such check, so h2 simply added 10.18.0.11 as a secondary address and printed no warning (see evidence/dad.txt).

3. Value of Version Control (Git Diff)

git diff shows exactly which lines of topology.yaml changed and nothing else. When I corrected my student_id_last4 and IPv6 block from fd00:2318 to fd00:3218, the diff listed just those lines with - and +, and when I removed the s2-s3 link to turn the loop into a tree, it showed that single line as removed. The commit message records why I made each change. With copies named topology-v2-final I would have to compare whole files by eye, and I could not tell who changed what, or when, or go back to one exact earlier version.
